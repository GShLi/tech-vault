# 知识库列表与详情交互审查

日期：2026-10-22。检查方式：本地浏览器实际操作 + 前后端代码核对。

本轮检查列表、详情、上传入口、新建表单、归档确认和成员管理流程。未执行归档、上传或成员权限变更；唯一提交为超长名称校验，服务端拒绝创建。以下区分实测复现与代码确认，业务代码未调整。

## 优先修复

### UX-01 · 高：从详情上传时默认选错知识库（已复现）

1. 列表进入“Java 官方文档 · 生产验收 2026-10-21”。
2. 点击“上传文档”。
3. 路径仍为该知识库的 `/upload`，但目标知识库变成“Java 验收异常样本”。

`DocumentUploadView.vue:41` 未读取路由的 kbId，默认选择列表第一项。用户信任当前上下文时会上传到错误的库。

建议：以路由知识库为默认目标，明确显示其名称；没有权限或不存在时阻止提交并解释，不能静默换库。跨库上传应是显式选择。

### UX-02 · 高：保存失败信息在弹窗背后（已复现）

新建时输入 121 个 A 并保存，服务端拒绝，但表单没有字段错误；背景页面出现 `Request validation failed.`，被遮罩挡住。名称字段仅配置必填，没有与后端一致的 120 字符限制。

`KnowledgeBasesView.vue:90,175,300`：保存和列表请求共用 error；“重试”实际重新加载列表，并不重试保存。

建议：弹窗内显示保存错误，名称旁提供中文校验及长度提示；列表加载与表单保存使用独立错误状态。版本冲突提供“重新加载并核对修改”的路径。

### UX-03 · 高：成员调整可能让操作者失去访问入口（代码确认）

成员选择可取消自己或全部成员，保存前没有影响提示。`kbs.py:update_kb_members` 允许空数组并替换成员；`kb_access.py:knowledge_base_or_error` 要求当前用户是有效知识库成员。保存后前端再次加载成员列表可能收到 404，用户会把“变更成功但失去权限”误认为保存失败。

建议：明确“谁可以访问”的含义；移除自己时单独确认后返回列表，或按产品规则限制最后一个管理者退出。至少保证存在可在界面恢复的管理路径。成员表单增加变更检测、取消、成功反馈和离开保护。

### UX-04 · 高：详情中的最近任务不属于当前知识库（已观察，代码确认）

Java 官方文档详情显示了之前上传至异常样本库的 Spring Boot 任务 `01M5FHSWVY1J300RS43DH77710`。

`KnowledgeBaseDetailView.vue:81` 读取整个团队的任务后取前五条；“全部任务”也直接跳到团队任务中心。

建议：服务端按知识库过滤；任务展示文档名、处理阶段、时间及失败原因摘要；进入任务中心时保留知识库筛选。

补充：列表后端文档数统计所有未删除文档，而详情计数来自当前用户可见的文档数组。存在私有文档时可能出现“列表有 N 篇，进入只看到 M 篇”的差异，应统一可见数量口径或明确解释。

## 建议调整后的主流程

- 列表：搜索/筛选 → 进入知识库；新建 → 自动进入新库详情。
- 详情默认文档区：上传/搜索文档；成员与设置作为独立管理入口。
- 上传：固定当前库上下文 → 上传完成 → 查看解析/索引进度 → 可用后开始问答。
- 成员：进入编辑 → 看见新增/移除变化 → 明确提交结果；退出自身访问范围时有单独处理。
- 归档：解释影响 → 确认 → 明确恢复方式或不可恢复的界面限制。

优先顺序：UX-01、02、03、04 → 上传闭环和归档 → 信息结构与检索效率。
